# ANS-100 Trainable Sequence Decoder V1

## Status

The Android branch contains a small trainable Elman recurrent neural network for next-token prediction. It is an experimental local component, not a pretrained Russian language model and not evidence of general language understanding.

The decoder is wired into the Android conversation response generator, but it only takes the learned-generation path after a model has been explicitly trained, restored from a valid snapshot, and its output passes conservative token-count and confidence gates. Until then, the existing bounded ANS response strategy remains active.

## Model

- Tokenizer: deterministic Unicode subword tokenizer for question/answer training, with a character fallback and explicit word-start markers. The legacy full-sequence training path remains word-level.
- Vocabulary: reserved BOS, EOS and UNK tokens, mandatory character pieces, and frequency-ranked 2–4 character word pieces, bounded by the configured vocabulary size.
- Network: one recurrent hidden layer with tanh activation.
- Objective: next-token categorical cross-entropy.
- Training: prompt-conditioned sequence back-propagation through time with clipped gradients; in question/answer mode, the prompt is context and only the answer plus EOS is supervised.
- Decoding: bounded deterministic beam search with repetition penalties and explicit EOS handling.
- Limits: at most 256 training examples, 64 subword tokens per prompt/answer pair, 512 vocabulary entries, 64 hidden units and 48 generated tokens.

There are no pretrained weights, cloud calls, Qwen calls, prompt templates or hidden language-model dependencies in this decoder.

## Persistence

The model snapshot stores its format version, architecture size, tokenizer mode, vocabulary, input/recurrent/output matrices and biases. Version-1 word-level snapshots remain readable; new snapshots use version 2. The snapshot is validated completely before it replaces the active model.

Android stores snapshots in an app-private file through AtomicFile; it does not place large neural matrices in SharedPreferences. The language module trains a candidate model and publishes it as active only after the durable snapshot write succeeds. A malformed or unreadable snapshot is not silently overwritten.

## Learning safety

Incremental fine-tuning is accepted only for:
- an explicit user correction; or
- an independently verified external outcome.

The following are not accepted as labels:
- text generated by the decoder itself;
- passive user behavior or inferred engagement.

This prevents the system from reinforcing its own unverified output as if it were ground truth.

Correction learning uses the prompt as recurrent context and supervises only the corrected continuation (plus its end marker). Prompt tokens are not treated as desired output labels, while gradients can still flow through the prompt state so the network can adapt the context representation.

## Chat integration

ANS100NeuralResponseGenerator can call the trainable decoder after a model has been loaded or explicitly trained. Capability, greeting, farewell and correction paths remain deterministic. Learned text is accepted only when the prompt is fully represented by known model pieces, it contains at least two generated tokens, and mean token confidence is at least 0.25. Subword composition reduces whole-word UNK failures but does not guarantee linguistic quality. The confidence is a decoder score, not a calibrated probability of factual correctness.

The ViewModel exposes explicit training, correction-feedback, generation and status methods. No automatic training corpus is bundled: training examples must be supplied deliberately. Until a sufficiently broad and independently reviewed Russian corpus is available, output quality and generalization are not established.

## Android training screen

The Android app exposes a dedicated **Обучение** tab for the experimental sequence decoder:

- model status shows whether weights are trained/restored, vocabulary size, hidden width, and storage errors;
- training data can be entered manually or imported from a UTF-8 TXT file (`prompt => answer` per non-empty line, lines beginning with `#` ignored; import is capped at 512 KiB);
- full training is explicit and replaces the previous model only after candidate weights are saved successfully;
- a separate correction form uses the prompt as recurrent context and supervises only the corrected continuation;
- an independent held-out form accepts `prompt => expected answer` lines and runs generation without applying any learning update.

The held-out screen reports case-insensitive exact-string match, token-overlap F1 and a coarse repetition rate. These are diagnostics only: they do not establish semantic accuracy, factual correctness, grammatical quality or general intelligence. Keep held-out examples separate from training and corrections. Training and evaluation run on a background executor rather than the Compose UI thread.

The screen does not bundle a corpus or silently learn from conversation history. Until a reviewed Russian corpus is supplied and evaluated, a trained decoder remains a small experimental model and may produce poor or empty continuations.

## Reproducible toy corpus (not a quality benchmark)

A deliberately tiny, hand-authored Russian smoke corpus is stored under `datasets/sequence_decoder_v1/`:

- `train_ru_toy.txt`: 81 short synthetic `prompt => answer` pairs. Import this file in the **Обучение** tab as training data.
- `heldout_ru_toy.txt`: 8 distinct prompts in the app's `prompt => expected answer` format. Load these only in the held-out evaluation field; do not train or fine-tune on them.

The held-out prompts are not copied verbatim from training. The two files nevertheless share a narrow, repetitive request/response style and much of the vocabulary. Therefore, this is only a pipeline smoke check for import, training, generation and evaluation wiring. It is not an independent measure of Russian language ability, semantic understanding, factual accuracy or generalization to ordinary conversation. A small Elman RNN may fail most or all exact matches; do not tune repeatedly against the held-out file and then report that score as an unbiased test.

For a meaningful evaluation, create a larger reviewed corpus from independently authored examples, split by intent/topic before training, keep the final test set sealed, and report exact match, token-level metrics, loss, repetition and human review separately.

### Evaluation diagnostics

The held-out evaluator now reports three separate diagnostics:

- case-insensitive exact-string match;
- mean token-level F1, calculated from multiset token overlap (so repeated words count, but word order and meaning are not assessed);
- repeated-token share in generated output, as a coarse repetition warning.

These metrics must be read together. Token F1 is not semantic similarity, factual correctness or grammatical quality; the repetition share is not a complete language-quality metric. The held-out set remains a toy pipeline check and must not be used repeatedly for tuning and then presented as an unbiased benchmark.

### Evaluation metrics

The held-out evaluator also reports:
- **Token-F1**: overlap of normalized generated and expected tokens, treating tokens as a multiset. It ignores token order and therefore must not be interpreted as semantic similarity.
- **Repetition rate**: fraction of generated tokens beyond the first occurrence of each distinct token within that answer. This is a coarse repetition diagnostic, not a fluency score.

These metrics complement exact match but do not replace human review. An answer can have a high token overlap while being grammatically wrong, misleading, or semantically reversed.

## Prompt-conditioned training update

The decoder now exposes `trainPairs` and the Android training tab uses this path. Each row must be `prompt => answer`. The vocabulary is built from both sides, the recurrent state is advanced through BOS and the prompt, and the loss is applied only to answer tokens and EOS. Prompt tokens are therefore context rather than labels that the model is asked to reproduce. The same raw prompt can be passed to generation, avoiding the earlier mismatch between training on tagged full lines and inference on a user's untagged question.

The legacy full-sequence `train` method remains for next-token sequence experiments and compatibility, but the Android question-answer training screen no longer uses it. The correction-learning path continues to supervise only the corrected continuation.

Unit tests were added for answer-only target counting, loss reduction on a tiny repeated pair set, generation from the same prompt, and persistence/restoration of pair-trained weights. These tests have been authored but have **not** been run; no Android build or CI was started.


## Subword generation update

Question/answer training now builds a deterministic word-piece vocabulary from the supplied corpus. Frequent pieces of up to four characters are available, and every observed character is retained as a fallback (with separate word-start pieces). This allows the decoder to compose a word it has not seen as a complete token when its characters were represented in training. It does not provide open-vocabulary understanding: unseen characters can still map to UNK, and the small recurrent network may still generate malformed text.

The model snapshot format is now version 2 and records the tokenizer mode. The reader remains backward-compatible with version-1 word-level snapshots. The ANS response generator rejects learned continuations when any prompt piece is unknown, then falls back to the conservative Core response path. The model remains a small experimental Elman RNN, not a production-scale language model.

## Context-conditioned ANS generation

The response generator now assembles a bounded context package from the current
conversation before invoking the ANS-owned decoder:

- up to four recent dialogue messages, with explicit user/ANS role markers;
- only user-approved memories already selected by the Core memory matcher;
- the current Core understanding: intent, key terms, entities and a bounded
  reasoning-plan excerpt;
- optional sparse-neuron telemetry, explicitly labelled as telemetry rather
  than semantic proof.

The current user prompt is appended after this context and remains the final
input segment. The context package is capped at 3,500 characters; individual
history excerpts and neural telemetry are separately bounded. The module also
rejects oversized combined input before inference.

This is context routing into the recurrent state, not proof that the decoder
understands or correctly follows every context item. The decoder's existing
unknown-token gate remains active: if any context or prompt piece is outside
the trained vocabulary, the learned generation candidate is rejected by the
response generator and the conservative Core response path is used instead.
Consequently, toy prompt/answer training data will not automatically teach
dialogue-memory reasoning. Contextual training examples and held-out evaluation
are still required before claiming that learned generation uses these sources
reliably.

No external or pretrained language model is called by this path. No tests,
Gradle builds, APK builds or CI workflows were run for this change.

## Context-conditioned training corpus V1

Two additional UTF-8 toy files exercise the exact context markers emitted by
`ANS100NeuralResponseGenerator`:

- `datasets/sequence_decoder_v1/context_train_ru_toy.txt`: 24 synthetic
  prompt/answer rows covering approved memory and recent dialogue. Several
  questions are deliberately repeated with different facts or preferences so
  the target answer must change with context.
- `datasets/sequence_decoder_v1/context_heldout_ru_toy.txt`: 8 separate
  context/question rows for a first held-out smoke evaluation. They use
  different facts and question formulations; keep them out of training and
  correction feedback.

Each left-hand side contains the context prefix followed by the current
question, matching the runtime's order: dialogue context, approved memory,
ANS analysis, then the current user prompt. Import the training file in the
**Обучение** tab as ordinary `prompt => answer` pairs. After training, paste
the held-out file only into the held-out evaluation field. Training replaces
the active candidate model after its snapshot is saved, so export/back up any
model snapshot that must be retained before experimenting.

The rows are intentionally short to fit the decoder's 64-subword-token
per-pair bound. They are synthetic and repetitive, and their expected answers
are simple recall statements. They test whether the pipeline can condition on
small context differences; they do not demonstrate robust long-context
reasoning, reliable memory retrieval, conflict resolution, general Russian
conversation or factual understanding. The held-out set is only eight examples
and must not be used for repeated tuning followed by a benchmark claim.

No model was trained from these files in the repository, and no test, Gradle
build, APK build or CI workflow was run while adding them.

## Bounded beam decoding and prompt-priority context

The decoder's inference path now uses a fixed-width beam search (width 3) instead of committing to a single beam-search next token at every step. Candidate sequences are ranked with a length-normalized log score. A small token-repeat penalty and an additional repeated-bigram penalty discourage simple loops. EOS remains an explicit candidate, and decoding stops when all retained candidates have ended or the configured token budget is reached.

The search is deliberately small and deterministic: it does not sample randomly, does not increase model parameters, and has a predictable upper bound suitable for a phone. Beam search explores alternatives under the learned model; it cannot make weak training data or an undertrained network produce reliable language by itself. The reported mean token confidence is the geometric mean of selected token scores and is still not calibrated factual confidence.

Context packing was also corrected. The decoder now tokenizes the current user prompt separately and reserves its token capacity first. Only the remaining portion of the 64-token input window is filled with the most recent context pieces. A long history/memory prefix can therefore no longer evict the beginning of a current prompt that fits the model's input window. If the current prompt itself exceeds 64 tokens, its earliest tokens are still truncated to preserve the latest part; this remains a known limit.

Regression tests were added for deterministic generation, output bounds, reserved-token filtering, and preserving a full 64-token current prompt when older context is present. These tests have not been run. No Gradle build, Android test task, APK, CI workflow, or device benchmark was run for this change.

The response generator now also rejects a learned candidate that simply runs out of its token budget mid-answer. It accepts a continuation only when the decoder emitted EOS or the rendered text ends with a sentence boundary (`.`, `!`, or `?`); otherwise the conservative ANS/Core path is used. This avoids presenting an obviously truncated fragment as a completed answer, at the cost of falling back more often until the model learns reliable stopping behavior.


## Multi-turn dialogue corpus V1

Two additional UTF-8 files exercise reference resolution across several recent
messages and deliberate topic switching:

- `datasets/sequence_decoder_v1/multiturn_train_ru_v1.txt`: 32 synthetic
  context-to-answer rows. The examples cover switching between two topics,
  returning to a deferred topic, distinguishing which project or requirement a
  follow-up refers to, and recovering the first/second item in a short plan.
- `datasets/sequence_decoder_v1/multiturn_heldout_ru_v1.txt`: 8 different
  context-to-answer rows reserved for a first diagnostic evaluation. Their
  scenarios and key nouns are not copied from the training rows.

Import only the training file in **Обучение** as `prompt => answer` pairs.
Use the held-out file only in the independent evaluation field. Do not train
on held-out answers or feed them back as corrections. Keep the earlier toy
corpora separate when comparing results so the source of each training run is
known.

The examples intentionally use the runtime's `[dialogue context]`, `user:`
and `ans:` markers. They are short because the decoder has a bounded
64-subword-token input/target limit. This corpus is still synthetic, small and
highly structured. It does not prove that the model can robustly track arbitrary
topics, resolve ambiguous pronouns, remember long conversations, or converse
naturally. A model can also memorize these patterns without learning a general
dialogue policy.

The training file is suitable for a controlled pipeline experiment, not as a
claim of language-model readiness. Before using results as evidence, review
generated answers manually and compare against a separately authored,
topic-disjoint evaluation set. No model was trained from these files; no tests,
Gradle build, APK build, CI workflow or device benchmark was run when they were
added.

## Speech output

Chat responses can be read aloud using Android's built-in TextToSpeech engine. Each assistant message has a **🔊 Озвучить** action, and the chat has an **Автоозвучка** switch for newly generated answers. The switch is saved in app preferences and is off by default.

The speech controller requests a Russian voice, prefers an installed local Russian voice when available, and uses a slightly lower pitch and measured speaking rate for a calm assistant delivery. The exact timbre and naturalness depend on the TTS engine and Russian voice packs installed on the device; this is not a clone of a film actor or an exact reproduction of the fictional JARVIS voice. No audio model is bundled, so app size and neural-model RAM use do not increase materially.
